# Qbar 前缀、英文缩写与拼音搜索实施计划

日期：2026-09-28。

状态：已实施，未运行验证。本文记录已落地的实现、工作顺序和静态验收范围。

## 1. 目标与完成标准

用户已选择使用 `pinyin-pro`。本期扩展 Qbar 普通候选项搜索，使开始菜单中的“网易云音乐”能通过 `wyy` 找到，“Visual Studio Code”能通过 `vs` 找到。大小写不影响匹配。

两个示例不添加硬编码别名：从名称自动生成搜索键，其他符合相同规则的名称获得相同行为。前提是应用已进入现有 Qbar 候选集合，例如有被现有扫描规则收录的开始菜单快捷方式。本期不扩展应用发现范围。

| 名称 | 生成的关键搜索键 | 必须命中的输入 |
| --- | --- | --- |
| 网易云音乐 | 全拼 `wangyiyunyinyue`、首字母 `wyyyl` | `网易`、`wyy`、`WYY`、`wyyyl`、`wangyi` |
| Visual Studio Code | 小写名称、英文单词首字母 `vsc` | `visual`、`vs`、`VS`、`vsc`、`studio` |

`wyy` 是 `wyyyl` 的前缀，`vs` 是 `vsc` 的前缀。英文首字母与汉字拼音首字母分别生成，不能用删除所有非字母字符的方法代替单词首字母提取。

“搜出来”指结果列表出现可选择的应用，并且选中后能够通过原执行链启动。AI 不再作为普通输入的默认结果；必须显式输入 `q` 或 `ai`，例如 `q 天气怎么样` 或 `ai 解释这段代码`。因此 `wyy`/`vs` 只展示匹配应用，选中应用行后 Enter 或点击该行即可执行。

## 4. 确定的架构

采用“页面生成搜索键，AHK 缓存并匹配”的方案。

1. AHK 继续持有候选真实对象、short、类型、配置值、快捷方式路径和图标信息。
2. 索引预热时，AHK 向现有 Qbar WebView2 发送候选 ID 与显示名称。
3. 页面使用本地 `pinyin-pro` 浏览器发行包生成拼音键，同时生成英文单词首字母键。
4. 页面一次性回传搜索键；AHK 校验消息并原子安装当前快照的键缓存。
5. 后续每次输入仍由 AHK 查询，使用字符串前缀和包含判断；页面不参与逐次拼音转换。
6. 图标、执行、历史与文件夹导航继续使用原候选数据。

此方案复用成熟启动器中“缓存候选拼音表示，再交给匹配器”的做法，也能保留当前 Qbar 查询路由。与库的 `match()` 相比，本期只需要预生成的可解释搜索键，因此使用 `pinyin()` 转换 API；无需逐个候选、逐次输入调用拼音匹配函数。

AHK 与页面之间全部异步。不得在 WebView2 消息回调中同步等待页面返回，或创建额外 WebView2。

## 6. 搜索键生成规则

### 6.1 原始名称和执行字段

- `label`、`short`、`value`、`type` 保持原义，派生键单独存放。
- 原始文字匹配继续遵循现有 AHK 大小写不敏感规则，不对执行文本做拼音替换。
- 用户查询只沿用当前去除首尾空格和制表符的操作，不删除参数、标点或路径分隔符。
- 新增缩写/拼音通道仅接受完整查询匹配 `^[A-Za-z]+$` 的输入，并转为小写。带空格的命令参数、路径和通配符不进入该通道。

### 6.2 中文全拼与首字母

对包含汉字的名称，使用固定选项 `toneType: 'none'`、`type: 'array'` 调用 `pinyin()`，随后生成全拼串和每个汉字拼音的第一个字母。实施时核对固定发行版的非汉字输出和数组对齐规则；不能假设所有 token 都是单个汉字。

为使规则明确，将名称按 Unicode 汉字连续段拆分；对每个连续汉字段调用库并分别生成一组 `pinyinFull`、`pinyinInitials` 键。汉字识别使用 WebView2 支持的 Unicode Script=Han 规则。多个段各自保留，去重，不跨标点和英文片段拼接。

例如 `网易云音乐` 形成一个段，首字母为 `wyyyl`；`网易云 Music` 的中文键为 `wyy`，英文部分另行提取。库无法转换的段不生成半截拼音键，原文字匹配仍然可用。

全拼规范化为小写、无声调，并明确把 `ü` 规范化为 `v`；本期允许 ASCII `lv` 这一输入形式。首字母从同一次全拼转换结果派生，避免两次转换产生不一致读音。

### 6.3 英文单词首字母

- 以空白、连字符、下划线和其他非 ASCII 字母数字字符分词。
- 在分词前识别常见驼峰边界，例如 `VisualStudioCode` 拆为 `Visual / Studio / Code`；大写缩写后接常规单词时，`XMLParser` 拆为 `XML / Parser`。
- 每个 token 取第一个 ASCII 字母；纯数字 token 不贡献字母。仅一个有效 token 时不生成英文缩写键。
- `Visual Studio Code`、`VisualStudioCode` 均得到 `vsc`；查询 `vs` 对其做前缀判断。
- 不将名称中的任意 `v` 与任意 `s` 组合成缩写，因此只含这两个字母的其他名称不会仅因此命中。
- 英文缩写和拼音首字母通道要求输入至少 2 个字母；全拼前缀也采用至少 2 个字母，降低单字母查询的噪声。

## 7. 匹配与排序合同

每个候选检查所有适用通道，取最优等级；一个候选只生成一条结果。

| matchRank | 条件 |
| --- | --- |
| 0 | 原 label 或 short 与完整查询相等 |
| 10 | 原 label 或 short 以完整查询开头 |
| 20 | 英文单词首字母或拼音首字母与查询完全相等 |
| 30 | 英文单词首字母或拼音首字母以查询开头 |
| 40 | 中文全拼键与查询相等 |
| 50 | 中文全拼键以查询开头 |
| 60 | 原有 label 包含匹配或显式通配符命中 |

精确 `short = firstToken` 的原有行为仍然使结果 `pinned = true`，包括携带参数的配置命令。若因精确首 token 命中而没有适用的完整查询等级，赋等级 0。隐藏被同名配置覆盖的 Everything 提示行的判断先于匹配。

输入含 `*` 或 `?` 时只走原有通配符与精确触发词通道，不对通配符尝试拼音转换。全拼和首字母本期只做相等/前缀判断，不增加拼音中间包含或任意跳字匹配。

普通结果按以下稳定顺序展示：

1. 原有 `pinned` 优先。
2. `matchRank` 升序，缺失值视为 60。
3. 原有 `TYPE_RANK`。
4. 原有 `label.localeCompare()`，同名再按候选原始序号稳定排序。

历史模式保留后端顺序。文件夹模式保留现有类型/名称顺序，不套用新等级。普通结果不再合成默认 AI 行；AI 只由显式 `q`/`ai` 输入进入执行分发。

必须在 `QbarSendResults` 显式传递 `matchRank` 和稳定序号。渲染、方向键选择、Tab 补全与 Enter 执行必须共享同一种排序函数，避免看到 A 行而执行 B 行。

## 8. 消息协议与缓存

### 8.1 快照身份

新增独立、单调递增的 `searchGeneration`，代表一次搜索键构建。候选 ID 是该快照内的唯一整数，不以 label 或 short 作为 ID，避免同名配置/应用互相覆盖。

`searchGeneration` 不复用用户查询 `queryId`、AHK `QbarQuerySeq` 或配置 `QbarConfigIndexGeneration`。配置 generation 用于判定快照是否仍基于当前配置，搜索 generation 用于识别跨重建、关闭、页面重载的过期回包。

### 8.2 AHK → 页面

拟新增入口 `window.buildQbarSearchKeys(payload)`，通过现有 `QbarExec` 和 JSON 序列化发送：

```json
{
  "generation": 12,
  "items": [
    { "id": 1, "label": "网易云音乐" },
    { "id": 2, "label": "Visual Studio Code" }
  ]
}
```

只发送 ID 与名称；执行路径、参数和配置值保留在 AHK。一次构建每批处理 50 个名称，通过页面定时器让出事件循环；新 generation 到达后停止旧批次。回传最终完整结果，不在中间批次启用输入。

### 8.3 页面 → AHK

拟新增消息类型 `searchKeysReady`：

```json
{
  "type": "searchKeysReady",
  "generation": 12,
  "ok": true,
  "items": [
    { "id": 1, "pinyinFull": ["wangyiyunyinyue"], "pinyinInitials": ["wyyyl"], "wordInitials": "" },
    { "id": 2, "pinyinFull": [], "pinyinInitials": [], "wordInitials": "vsc" }
  ]
}
```

整个构建失败时发送 `ok: false` 和固定错误码，例如 `dependency_missing` / `conversion_failed`；不回传调用堆栈或带候选名称的错误正文。某个名称不能转换时可返回该项空拼音数组，其他项继续构建。

AHK 复用 `LLMMessageParse` 解析外层 Map。数组从解析结果读取并验证类型，不能通过仅用于标量的 `LLMMsgField` 获取数组。验证 generation 为当前待处理整数、ok 为布尔值、每个 ID 有效且不重复、结果数量和快照一致、字段类型正确。

键只允许规范化后的 ASCII 小写字母。每个键的长度按源名称长度设置合理上界（全拼可按 Unicode 字符数的 8 倍），段数不超过名称字符数。回包不携带可执行字段，AHK 仅将键附加到原快照对象。

只有整包验证通过才原子替换缓存。旧 generation、取消后的回包、重复完成消息直接忽略；无效当前回包进入原有文字匹配降级路径。

### 8.4 生命周期

| 事件 | 处理 |
| --- | --- |
| 首次打开 | 扫描现有开始菜单缓存 → 建立候选快照 → 请求生成键 → 安装缓存 → 启用输入并恢复预填查询 |
| 隐藏后再次打开，缓存仍有效 | 直接复用 AHK 搜索键缓存，不重新转换名称 |
| 设置保存引发配置索引失效 | 同时使搜索键缓存失效、递增 generation；可见时延迟重建，隐藏时下次打开重建 |
| 可见状态重建 | 暂停输入、清除旧结果并使旧查询序号失效；保留当前完整输入，完成后重新查询 |
| 重建期间再次变更配置 | 取消旧构建，新快照采用最新配置 generation |
| 构建期间隐藏 | 取消待处理构建和超时定时器，递增 generation；再次打开按当前状态重建 |
| 页面重载/重新创建 | 旧待处理请求失效；已安装在 AHK 的有效缓存可复用，未就绪时重新握手 |
| 关闭 Qbar 宿主 | 取消所有搜索构建定时器、清理待处理状态；保留或释放已完成缓存应与现有宿主关闭生命周期一致 |

不要仅检查原 `QbarIndexReady` 就提前结束预热：它代表现有基础索引，而新增搜索键有独立的 `idle/building/ready/degraded` 状态。

所有取消和完成入口幂等。可见状态重建恢复的是重建前当前输入，不能误用仅在打开时设置的 `QbarPendingText` 覆盖用户已经输入的内容。IME 组合输入期间延后可见重建，待 compositionend 后执行；已有查询序号机制继续阻止过期结果覆盖新输入。

### 8.5 失败与超时

请求页面生成搜索键后启动 5 秒一次性 AHK 定时器；正常完成或取消时停止。超时后取消该 generation，进入 `degraded` 并启用输入，使用原文字、精确触发词和通配符匹配。日志只记录状态和数量。

同一次打开会话内不自动无限重试；下次打开或候选配置变更可重试。页面缺失第三方库时同样恢复基本搜索，不能永久停留在 loading。降级不宣称拼音功能正常；实现完成报告应明确未运行验证。

## 9. 执行、图标和历史衔接

- 搜索命中的返回行仍提供候选原始 `short` 和 `type`。例如查询 `wyy` 命中后，选中行携带“网易云音乐”，不能把 `wyy` 当作启动命令。
- 应用行继续经过 `QbarExecute` → `QbarFindByShort(QbarStartMenuItems(), text)` → `QbarRunShortcut`。
- Tab 补全仍填入原 short，不填拼音或首字母键。
- 不因相同名称合并不同类型候选；沿用当前配置优先和执行解析语义，不在本期重构命令身份。
- 仍只为匹配结果安排图标提取，建立键缓存时不预提取全部图标。
- 搜索键缓存不写入历史文件；成功启动后的历史条目继续记录原应用标签和真实目标。
- 每次新查询发出时清除旧可执行选择；新结果到达前 Enter 不执行上一轮选择或自动转 AI。页面以 pending-query 状态保护，compositionstart、重建、隐藏均使旧选择失效；setResults 只对当前 queryId 解除 pending。
- 空输入历史的 `executeHistory` 校验维持现有逻辑；新的普通结果排序不得改变历史 ID 和显示记录校验。

## 13. 风险与维护说明

默认词组读音可能与品牌特殊读音不同；首期使用单一词组读音可满足目标案例，后续若有具体漏搜案例，再依据案例添加库支持的自定义读音机制。不要通过多音字笛卡尔积扩大索引。

首次打开新增一次异步搜索键构建，批处理和超时可以限制对界面的影响，实际耗时需在用户以后允许运行验证时测量。本计划不作未经测量的性能保证。

英文 acronym、中文首字母通常会有重名命中，稳定排序和原始名称显示用于区分。应用发现和同名执行解析沿用现有实现，不能将既有扫描限制报告成拼音库问题。

后续升级依赖时，更新固定版本与哈希，重新静态核对输出选项、浏览器导出方式和许可证；不从 main 分支直接替换发行文件。
