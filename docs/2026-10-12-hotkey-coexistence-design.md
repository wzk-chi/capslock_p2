# capslock_p2 与笔试助手快捷键共存设计

日期：2026-10-12

状态：已生成助手键盘组件的独立候选 EXE，并完成另一份 AHK 的精确 Alt 匹配与 CapsLock 让位修改。两项均仅完成静态校验，尚未启动、重载或完成运行验收；capslock_p2 源码、原助手 EXE 和用户配置保持原样。实施范围见第 10、11 节。

后续 Ctrl+Shift+C 多模型组切换另见[多模型配置组设计](2026-10-12-assistant-model-profiles-design.md)，目前仅设计，尚未接入实际助手。

## 1. 目标与结论

用户希望 capslock_p2 与 `D:\work\招聘\笔试\PracticeDesktopAssistant_Local.exe` 同时运行、各自快捷键同时可用。其中 CapsLock 点按继续发送 Ctrl+Space，不能在启动笔试助手后恢复为系统大小写切换。

推荐方案：笔试助手改用 Windows `RegisterHotKey` 接收全局快捷键；capslock_p2 继续负责 CapsLock 层；另外一份正在运行的 AHK 收紧通配 Alt 映射。明确不同组合的归属，使正确行为不依赖启动顺序。

助手的五项功能与 Ctrl+Alt / Ctrl+Shift 入口均保留。F8–F11 保留普通功能键入口；F12 是 Windows 保留的调试键，不能作为普通系统全局热键注册。默认使用已有 Ctrl+Alt+Q / Ctrl+Shift+Q 终止操作；如还要求原样保留全局 F12，需采用第 5.4 节的单独接入，不悄悄改动或承诺无效的注册。

“同时生效”指两套功能均可独立使用。同一次物理按键在同一上下文中只执行一个所属动作；例如 F8 操作笔试助手，CapsLock+F8 控制 capslock_p2 的长按连发，不让一次输入同时启动两个功能。

仅调整 capslock_p2 的钩子顺序，可以作为缓解措施，不能对原样运行的外部 EXE 承诺完全无冲突。完整方案需要笔试助手配合修改；当前目录只有 EXE，源码或可修改版本是实施前提。

## 2. 已确认的证据与判断边界

### 2.1 capslock_p2 的配置与运行状态

- 数据库 `data/capslock_p2.db` 中，全局 `press_caps` 为 `keyFunc_send`，参数为 `["^{Space}"]`；没有查到笔试助手专属的 CapsLock 覆盖。配置仍然是 CapsLock → Ctrl+Space。
- 运行中的 capslock_p2 使用 `D:\utils\AutoHotkey\v2\AutoHotkey64.exe`，版本 2.0.13，进程已提升为管理员权限。笔试助手为普通权限，因此提高 AHK 权限不能解释或解决当前问题。
- capslock_p2 的暂停与禁用热键菜单均未勾选；日志在最后一次 CapsLock 记录之后仍有剪贴板事件，表明进程没有整体退出。
- 用户确认失效覆盖其他程序；在保持两个程序运行状态不变时，点按 CapsLock 三次仍切换大小写，日志没有新增 `CapsLockDown` / `CapsLockUp`。
- 拦截入口位于 `lib/input/keymap.ahk`，使用 `$CapsLock`；发送映射最终进入 `lib/input/keys.ahk` 的 `keyFunc_send()`。

可确认：此次失效发生在 CapsLock 动作正常分发之前，问题范围已缩小到键盘事件接收与拦截链。现有观察不能单独区分钩子未被调用、钩子被系统移除或其他监听器影响事件传递，不能写成“已证实某个程序删除了 AHK 钩子”。

### 2.2 笔试助手的键盘实现

检查对象 SHA-256：`1A459F2105718F218B3F6342537EC16C850E4D516D83E370EEDD3FBDC32C8644`。

该 EXE 为 PyInstaller 打包的 Python 3.13 程序。只读取打包数据并反汇编字节码，没有执行其中的代码。内嵌 `desktop_app.py` 的相关位置为：

| 位置 | 已观察到的行为 |
| --- | --- |
| `Win32BackgroundController._run`，原始行号 1054 起 | 优先安装键盘钩子；只有安装失败时才调用 `_register_hotkeys()`，并非同时启用两个全局入口 |
| `_install_keyboard_hook`，1110 起 | 调用 `SetWindowsHookExW(WH_KEYBOARD_LL, ...)`，监听全局键盘事件 |
| `_keyboard_hook_proc`，1127 起 | 命中助手动作后入队并返回 1，抑制对应按键；其他事件通过 `CallNextHookEx` 传递 |
| `_keyboard_hook_proc`，1145–1154 | F8–F12 只按虚拟键码匹配，没有限制额外修饰键，也没有检查物理 CapsLock 是否按住 |
| `_keyboard_hook_proc`，1155 起 | 使用 Ctrl 且 Alt 或 Shift 按住的宽松条件匹配 R/H/F/O/Q，没有排除其他额外修饰键 |
| `_register_hotkeys`，1231 起 | 已实现 Ctrl+Alt、Ctrl+Shift、F8–F12 的系统注册，使用 `MOD_NOREPEAT` |
| `DesktopApp.bind_hotkeys`，1926 起 | Tk 页面另有部分相同组合的局部绑定，修改全局入口时需核对重复分发 |

已确认的具体冲突：当笔试助手的钩子先接到 F8 时，CapsLock+F8 也可能被识别为助手的 F8，并被抑制；F9–F12 有相同问题。这是代码可直接推导的归属错误。

CapsLock 本身及 Ctrl+Space 不在助手钩子的动作集合中，普通 CapsLock 事件按该函数逻辑会继续传递。因此，目前不能把点按失效解释为“助手有一条直接吞掉 CapsLock 的规则”。它与外部钩子、AHK 发送及系统钩子状态之间的具体触发关系仍待运行观察补齐。

### 2.3 另一份 AHK 也参与了冲突

现场还运行着 `C:\Users\13356\Documents\AutoHotkey\main.ahk`。其中 `lib/common/MacHotkeys.ahk` 使用 `*!r`、`*!f`、`*!q` 等通配 Alt 热键。

`*` 允许额外修饰键，因此这些映射也匹配 Ctrl+Alt+R/F/Q；其他通配 Alt 字母同样会覆盖助手对应组合。它们还可能与 CapsLock+Alt 层争用。

如果只把笔试助手改成 `RegisterHotKey`，保留这份通配映射不变，助手快捷键仍可能在系统生成热键消息之前被拦截。完整共存设计必须覆盖这一已知参与者，不能只计算两个进程。

### 2.4 官方机制支持的判断

- [Microsoft：LowLevelKeyboardProc](https://learn.microsoft.com/windows/win32/winmsg/lowlevelkeyboardproc) 说明：钩子回调超时后，Windows 7 及以后可能静默移除钩子；系统不提供直接获知这一移除的方式。Windows 10 1709 及以后最多使用 1000 毫秒超时。
- 本机 `LowLevelHooksTimeout` 为 25000；该值不能突破上述系统上限，继续调大它不是修复方案。
- [AHK：SendMode](https://www.autohotkey.com/docs/v2/lib/SendMode.htm#SendInputUnavail) 说明：SendInput 对其他 AHK 钩子可回退发送方式，但不能检测所有非 AHK 程序的低级钩子，遇到这种钩子时可靠性可能下降。
- [AHK：InstallKeybdHook](https://www.autohotkey.com/docs/v2/lib/InstallKeybdHook.htm) 提供 `InstallKeybdHook(true, true)` 强制重新安装能力，既会恢复安装，也会改变钩子的优先顺序；成功调用不等于已证明后续键盘事件必然正常到达。
- [Microsoft：RegisterHotKey](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-registerhotkey) 明确 F12 始终保留给调试器，程序不应把它注册为全局系统热键。助手现有回退代码包含 F12，并不意味着该候选在系统注册方式下可用。

以上说明当前症状在技术上可能出现，不构成“本次一定发生了超时”的证据。

## 3. 方案取舍

评价标准：两边功能保留、启动顺序无关、组合归属明确、一次输入一次动作、修改可回滚、运行结果可观察。

| 方案 | 能解决什么 | 主要不足 | 决定 |
| --- | --- | --- | --- |
| 提高 AHK 权限或调大超时 | 部分权限导致的发送问题 | 当前 AHK 已提升；系统限制超时上限 | 不采用 |
| 先开助手、后开 AHK；失效后重载 | 暂时改变钩子顺序、恢复事件接收 | 重启或重新安装钩子后可再次改变；依赖用户操作 | 只用于诊断，不作为设计 |
| 定时强制重装 AHK 钩子 | 可能恢复被移除的钩子 | 两个程序仍争用输入；修复有空窗，可能扰动按住状态 | 不采用周期抢占 |
| 全部 SendInput 改成 SendEvent | 避开部分外部钩子与发送模式的组合问题 | 不解决助手宽松匹配、另一份 AHK 通配匹配，且改变全项目发送性能 | 不做无证据的全量替换 |
| 系统注册助手热键，AHK 保留层拦截，并精确匹配其他 AHK | 消除助手对所有键盘事件的全局接管；明确 CapsLock 与普通组合的归属 | 需要修改外部程序及相关 AHK，进行人工验收 | 推荐完整方案 |

选择理由：当前两个确定的归属问题都来自过宽的拦截，收紧输入所有权比依赖钩子安装先后更稳定。对于 CapsLock 点按中断，仍需验证改造后的现场表现，不能把设计当作已经修复。

## 4. 按键归属与预期行为

| 输入 | capslock_p2 | 笔试助手 | 另一份 AHK |
| --- | --- | --- | --- |
| CapsLock 点按 | 按现有点按规则发送 Ctrl+Space | 不触发动作 | 不接管 |
| 已支持的 CapsLock+字母 / 功能键组合 | 执行已配置的层动作 | 不触发对应普通快捷键 | 不接管 |
| CapsLock+F8 | 切换长按连发状态 | 不触发矩形选区 | 不接管 |
| 已支持的 CapsLock+左 Alt+按键 | 执行现有第二层动作 | 不触发普通组合 | Alt 模拟映射让位 |
| Ctrl+Alt+R/H/F/O/Q | 无 CapsLock 层动作时透传 | 分别执行选区、长按选区、全屏、转文字、终止 | 通配 Alt 映射不匹配 |
| Ctrl+Shift+R/H/F/O/Q | 无同组合的用户映射时透传 | 保留现有等效入口 | 不接管 |
| F8/F9/F10/F11，无额外修饰键 | 未进入 CapsLock 层且没有同键映射时透传 | 保留前四项功能的等效入口 | 不接管 |
| F12，无额外修饰键 | 默认保留已有应用/用户映射；选做接入见 5.4 | 默认不注册全局 F12，终止入口仍有 Ctrl+Alt+Q / Ctrl+Shift+Q | 不新增接管 |
| Alt+R/F/Q 等原有 Alt 映射 | 不在 CapsLock 层时透传 | 不匹配 | 保留原有模拟动作 |
| Ctrl+Space | 按原有应用及输入法行为处理 | 不匹配 | 不接管 |

本设计不扩展 capslock_p2 原本不支持的修饰键组合，也不改变短按、长按、录制及应用覆盖语义。

系统热键按精确的 Ctrl/Alt/Shift/Win 组合注册。F8 不应意外覆盖 Ctrl+F8、Alt+F8、Shift+F8。对于现有 CapsLock 层支持的 F8 等输入，由 AHK 在系统热键消息生成前拦截；这要求 AHK 钩子实际健康，仍须运行验收。

如用户以后把助手的同一组合配置为另一项 AHK 动作，需要指定归属或换一个触发组合。不能同时承诺两个相互抑制的动作都由同一次输入执行；可以在现有快捷键配置中显式设计一次动作调用另一功能，而不能静默双重触发。本次未发现 capslock_p2 有这样的助手组合覆盖。

## 5. 笔试助手的修改设计

### 5.1 全局入口统一为系统热键

后台控制器启动流程改为：

`创建现有后台窗口 → _register_hotkeys(hwnd) → 接收 WM_HOTKEY → 放入现有命令队列 → UI 执行动作`

复用已存在的系统热键 ID、命令队列及业务方法。默认不调用 `_install_keyboard_hook()`；系统注册失败时也不自动切回全局低级钩子，否则冲突会重新出现。

保留 Ctrl+Alt、Ctrl+Shift、F8–F11 入口及 `MOD_NOREPEAT`，不注册系统保留的 F12。逐项记录注册成功与失败。每项动作至少有一个可用入口；部分注册失败时向用户展示实际可用组合，全部失败时给出“该功能的快捷键被其他程序占用，请调整快捷键”的说明。错误码、PID、线程和注册 ID 进入诊断日志。

按官方定义补齐 RegisterHotKey / UnregisterHotKey 的参数和返回类型，窗口句柄使用指针宽度类型。重新注册与退出时只注销本程序成功取得的注册，不留下旧入口。

不得通过安装低级钩子强行夺取系统已判定被占用的组合；不得为解决占用而自动关闭其他程序。

### 5.2 避免 Tk 与全局入口重复触发

审查 `DesktopApp.bind_hotkeys()` 中与全局快捷键相同的绑定。在 Windows 后台控制器正常运行时，全局组合仅由 `WM_HOTKEY` 入队，不再由 Tk 对同一组合直接执行第二遍。

保留与全局快捷键无关的局部控件操作。对后台控制器不可用的情况，只允许明确的窗口内操作降级，并展示全局快捷键不可用状态；不能悄悄启用另一套全局监听。

通过统一入口和 `MOD_NOREPEAT` 避免一次按住多次触发，不使用长时间去重窗口吞掉用户有意的连续点按。

### 5.3 业务与数据保持原行为

截图、长按右键选区、转文字、终止生成、移动端同步、托盘及设置保存沿用原实现。本次修改限于键盘接入与重复分发，不涉及模型请求、界面改版或设置格式迁移。

AHK 发出的 Ctrl+Space 不对应任何助手入口。若用户显式把 AHK 动作映射成助手的可用组合，是否调用助手应按该映射的意图处理；不能统一屏蔽所有模拟输入来获得表面共存。

### 5.4 需要原样保留全局 F12 时

不能为这一别名恢复助手的全局键盘钩子。可由已经负责层拦截的 capslock_p2 接收普通 F12，再通过助手新增的明确命令接口提交一次“终止”动作；CapsLock+F12 继续归层内配置。这需要双方源代码配合，属于可选扩展，默认方案不偷偷接管用户的 F12。

接入必须复用现有快捷键动作注册与白名单，使用稳定动作 ID；只有精确路径匹配的助手运行、未进入 CapsLock 层、未录制且用户未为 F12 指定其他动作时才生效。不硬编码当前 EXE 的私有热键 ID，也不向不明窗口发送指令。助手只接受固定的终止命令，限制重复触发并立即入队，不传递任意函数名或可执行代码。

该扩展需要单独设计接口、失效提示和回滚，再增加启动顺序、F12 连按与 CapsLock+F12 验收。若不增加接口，则明确使用既有 Ctrl+Alt+Q / Ctrl+Shift+Q；五项功能仍然全部保留。

## 6. AHK 侧的修改设计

### 6.1 capslock_p2 保留现有输入架构

沿用 `keymap.ahk` 的层注册、`appProfiles.ahk` 的全局/应用覆盖及现有录制保护，不建立另一套快捷键注册表或硬编码助手动作。

不改用户的 `press_caps` 配置，不使用 `SetCapsLockState("AlwaysOff")` 掩盖失效；这会改变用户主动映射为大小写切换时的行为，也不能让 Ctrl+Space 恢复。

完整方案首先消除助手的低级钩子和已知通配冲突。保留现有 SendInput；如人工观察仍证明发送阶段失效，再针对实际失败入口评估 SendEvent，不在定位不充分时替换全部发送代码。

### 6.2 另一份 AHK 收紧匹配

在 `C:\Users\13356\Documents\AutoHotkey\lib\common\MacHotkeys.ahk` 中，将相关 `*!字母` 改为精确的 `!字母`，使 Ctrl+Alt 不再被当成普通 Alt 模拟组合。

该组映射还需在物理 CapsLock 按住时让位，可使用独立的 `#HotIf !GetKeyState("CapsLock", "P")` 条件，并在文件末尾恢复条件，避免污染后续模块。

实施前读取该目录适用的 AGENTS.md，独立核对其现有热键和数据；这是仓库外的单独修改边界，不混入 capslock_p2 的功能提交。收紧后，普通 Alt 模拟动作保留，过去被通配匹配到的 Ctrl/Shift/Win+Alt 组合恢复各自含义。

### 6.3 可选的人工恢复入口

若改造后的观察仍出现系统静默移除钩子，可在现有托盘加入“恢复快捷键”操作，调用官方 `InstallKeybdHook(true, true)`。它属于恢复能力，不代替输入归属修复，也不安排周期重装。

恢复只在物理 CapsLock、相关修饰键及活动连发按键均已释放、录制结束后执行；请求期间不忙等。复用现有状态清理，取消当前连发任务但保留模式启用状态，不在按住途中伪造释放或重放未知按键。

日志区分“已请求重新安装”和“随后收到了真实按键”，不能仅凭 API 调用成功标记所有快捷键已恢复。此项须由后续证据决定是否纳入实施，不是第一阶段必做项。

## 7. 实施前提与阶段

### 7.1 获取可维护的笔试助手修改入口

检查时只发现 EXE、使用说明、设置文件和结果文件；用户随后确认没有源码。打包字节码可用于定位和局部替换，但不能把反汇编视为已有完整、可维护源码。

首选获取对应版本源码，从源代码修改后台控制器后生成独立候选版本。若只能修改 EXE，需另立可回滚的单组件补丁方案，验证打包结构、Python 版本、启动及热键行为；不得把本次设计直接等同于可安全覆盖 EXE 的许可或技术结论。

候选程序、原文件备份及设置文件保持清晰边界。实施前核对原 EXE 的哈希；保留原件，不覆盖、删除用户设置或结果数据，不把含 API 凭据的 JSON 加入仓库。

### 7.2 建议实施顺序

1. 补齐基线观察：由用户退出助手后观察 CapsLock 是否恢复；如不恢复，再观察人工重载 AHK 后是否恢复。只用于区分持续拦截与已失效的钩子，不作为长期使用步骤。
