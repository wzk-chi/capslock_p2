## 3. 原问题、判断与验收条件（基线快照）

### A01：原生剪贴板写入使用空所有者

**证据。** [EverythingCopyFiles](../lib/features/everything/everything_actions.ahk) 以 `OpenClipboard(0)` 打开，随后在 114–117 行调用 `EmptyClipboard` 和 `SetClipboardData(CF_HDROP)`。[NotesSetClipboardImage](../lib/features/qbar/qbar_notes_actions.ahk) 也以空 HWND 打开，随后清空并写入位图/PNG。

Microsoft 的 [OpenClipboard 文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-openclipboard) 明确说明：以 NULL HWND 打开后调用 `EmptyClipboard` 会将所有者设为 NULL，导致 `SetClipboardData` 失败；另见 [SetClipboardData](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setclipboarddata)。两条业务路径均缺少清空后写入失败的原内容恢复。

**触发与影响。** 从 Everything 复制文件或从笔记复制图片时进入此路径；若清空成功而写入失败，复制失败且此前剪贴板内容可能已经丢失。源码与接口契约支持这一判断，本次没有运行复现。

**修复方向。** 使用有效的宿主 HWND，集中复用剪贴板打开、所有权转移、关闭和失败恢复逻辑。已有[历史恢复实现](../lib/features/clipboard/clipboard_formats.ahk) 使用有效所有者并备份原内容，可作为复用基础。位图句柄与 HGLOBAL 的释放规则不同，不能将所有格式机械套入同一内存释放方法；只读剪贴板时的 `OpenClipboard(0)` 也不应一概修改。

**验收条件。** 文件、位图和 PNG 写入都传入有效 HWND；打开失败不改内容；清空后失败有安全恢复和明确日志；句柄只释放或移交一次。运行场景验证需另获授权。

### A02：已有笔记读取失败后仍可用空编辑器覆盖原记录

**证据。** [NotesBeginEdit](../lib/features/qbar/qbar_notes.ahk) 在读取之前记住原 `noteId`；267–270 行把读取失败替换为空笔记，仍发送 `openEditor`。[NotesStoreReadNote](../lib/features/qbar/qbar_notes_store.ahk) 将查询失败和记录不存在都返回为 `0`，标签和附件查询失败也被折叠为空集合。[页面保存](../pages/qbar-notes.html) 会把值为 0 的 ID 变为空串，而 [NotesHandleSave](../lib/features/qbar/qbar_notes.ahk) 又将空 ID 回退为宿主保存的原 ID。[保存仓储](../lib/features/qbar/qbar_notes_store.ahk) 更新完整正文并重写标签，未核查 UPDATE 的受影响行数。

**触发与影响。** 打开已有笔记时发生暂时读取失败，用户在空编辑器输入并保存，保存时数据库已恢复可写，原记录即可被覆盖。仅标签读取失败时，保存也可能把真实标签替换为空集合。不是每次读失败都会发生数据丢失，但静态调用链具备这一条件。

**修复方向。** 区分 `ok / missing / error`；已有记录及其关联数据未完整读出时，不发布可保存的编辑会话。新建空笔记只能由明确的新建动作产生。保存目标绑定宿主编辑会话，核对页面 ID，并检查更新行数；不要把“未读取”当成“用户清空”。

**验收条件。** 正文、标签或附件读取失败均不能变成可覆盖原记录的空白编辑状态；记录消失时有独立结果；正常新建和正常编辑继续可用。置信度高，尚未运行复现。

### A03：一个 API 凭据不可解密会阻止整个应用启动

**证据。** [SettingsStoreLoad](../lib/app/settings_store.ahk) 解密任何一个 `cfg_secrets` 失败即抛错；[ConfigLoad](../lib/app/config.ahk) 将其视为配置加载失败；[Initialize](../lib/app/core.ahk) 随即 `ExitApp`。[README](../README.md) 却指引换电脑或 Windows 用户后重新填写凭据，当前启动链无法让用户正常进入设置完成该操作。

**触发与影响。** 迁移含当前用户 DPAPI 密文的数据库，或单条凭据损坏时，即使快捷键和其他本地数据完好，应用仍整体退出。

**修复方向。** 把“单个凭据不可用”和“数据库/结构化配置不可读”分开处理。保留不可解密的原记录，标记对应服务不可用，让设置页允许明确替换或清空。普通设置保存不得隐式覆盖未解密的凭据；不要用代码默认值掩盖普通配置损坏。

**验收条件。** 单条凭据失效仅阻止依赖它的功能，设置仍能打开；显式替换后恢复；普通设置保存保留原密文；数据库整体不可读仍明确报错。置信度高。

### A04：剪贴板历史配置无效时回退为默认开启

**证据。** [ClipboardHistoryPluginSettings](../lib/features/clipboard/clipboard_history.ahk) 包含 `enabled=true` 等代码回退值；命令/设置缺失时又逐字段使用 schema 默认值，没有核查 `settingsValid`。[QbarRegistry](../lib/features/qbar/qbar_registry.ahk) 会把无效设置置为空 Map 并禁用命令，但采集服务通过上述函数重新取到了默认值。[初始化](../lib/features/clipboard/clipboard_history.ahk) 将其直接赋给采集开关；[核心启动](../lib/app/core.ahk) 未以 Qbar 初始化成功作为后续条件。

**触发与影响。** 剪贴板插件持久化设置不完整或无效，或者注册表不可用而主库尚可使用时，可能把原本关闭的历史采集重新开启。这也违背运行时不回退代码默认设置的项目约束。

**修复方向。** 服务只接收经过校验的持久化设置快照；不可用时停止采集并使待处理任务失效，记录诊断，在设置页说明无法读取。首次建库的默认设置写入保留在初始化流程，不放在运行时读取函数内。

**验收条件。** 缺字段、无效字段和注册表初始化失败都不会自动开启采集；有效配置的开关和限制仍按保存值执行。不能将“Qbar 启动命令被禁用”直接等同于“采集关闭”，应分别明确其产品语义。置信度高，未操作真实配置验证。

### A05：同一主库连接存在多套有效性和事务控制

**证据。** [AppStoreTransaction](../lib/app/store.ahk) 在回滚失败时调用 [AppStorePoison](../lib/app/store.ahk) 停用连接。但 [AiChatStoreInit](../lib/features/aiChat_store.ahk)、[NotesStoreInit](../lib/features/qbar/qbar_notes_store.ahk)、[ClipboardHistoryStoreInit](../lib/features/clipboard/clipboard_store.ahk)、[QbarStoreInit](../lib/features/qbar/qbar_store.ahk) 各自缓存 Ready 和同一连接的引用，命中缓存后不再核对主库有效性。

同时，对话保存（`aiChat_store.ahk:168–224`）、笔记保存（`qbar_notes_store.ahk:465–510`）、剪贴板保存（`clipboard_store.ahk:162–243`）和 Qbar 事务入口（`qbar_store.ahk:153–162`）分别执行事务指令；多处回滚失败只被忽略，没有统一停用该连接。

**触发与影响。** 主库被标记不可用后，已经初始化的功能仓储仍可能继续使用旧连接；功能仓储自身回滚失败时，也未完整进入全局停用路径。这里已有 `Critical` 等保护，不能据此断言正常操作必然发生嵌套事务或数据损坏。

**修复方向。** 保留各领域仓储和 SQL 职责，将连接有效性、事务所有权、提交/回滚与回滚失败处理统一到 AppStore。已有设置保存事务内的 Qbar 写入要走明确的事务参与路径，不能把每个子操作都再包一次事务。无需新增通用 ORM、事务队列或其他数据库。

**验收条件。** 所有仓储读取共同的连接状态；回滚失败后所有新操作拒绝继续；任何保存路径只有一个事务所有者；原设置整体原子保存不被拆散。异常路径判断置信度高，发生频率未知。

### A06：截断或解析丢块的流式回答可能被标成完整成功

**证据。** [LLMStreamFinishReason](../lib/shared/llm.ahk) 提取任意非空结束原因；[事件解析](../lib/shared/llm.ahk) 对 JSON 解析失败仅增加 `parseErrors` 并丢弃事件；[结束判定](../lib/shared/llm.ahk) 在有正文且存在任意结束原因或 done 标记时仍可返回成功。[AiChatStreamFinished](../lib/features/aiChat.ahk) 将成功结果写成 `complete`，并加入后续模型上下文。

**触发与影响。** 返回 `finish_reason=length` 等非正常完成原因，或者部分内容事件解析失败后仍收到完成标记时，用户可能看到不完整回答却没有相应状态，下一轮上下文也按完整回答使用。

**修复方向。** 明确正常完成、长度截断、内容限制、未支持的工具调用和流解析异常的映射；保留已收到的内容，但把不完整状态贯穿 UI、持久化和上下文策略。合法的 usage/心跳/空 delta 不能被当成损坏事件；具体哪些不完整内容可继续参与上下文，应有明确规则。

**验收条件。** 正常文本仍可流式完成；长度截断和损坏内容事件不再默认为完整回答；用户能看到已保存的部分内容及可采取的下一步。源码判断置信度高；本次没有观察到对应服务端异常响应。

### A07：标签编辑未处理保存结果

**证据。** [标签消息分支](../lib/features/qbar/qbar_notes.ahk) 调用新增/重命名仓储后直接刷新，未使用保存结果；删除标签也缺少对应失败结果。[NotesStoreRenameTag](../lib/features/qbar/qbar_notes_store.ahk) 可以返回 false，标签名有唯一性约束。相比之下，同文件 [NotesHandleSetCycleCopyTag](../lib/features/qbar/qbar_notes.ahk) 已有明确结果回执，删除笔记和置顶也已有回执，不应把问题扩大到全部笔记动作。

**触发与影响。** 将标签改成另一个已有标签名会违反唯一性约束；数据库写入失败也进入同一路径。用户只看到刷新后的旧值，无法判断失败原因和是否需要重试。

**修复方向。** 为标签操作返回明确成功/失败结果；重复名称给出可理解的提示，存储异常记日志，失败时保留输入。直接复用现有消息回执和 AppToast/AppDialog，无需通用命令总线。

**验收条件。** 重名、空名和写入失败都有结果；刷新仅发生在适当的成功路径；成功操作保持当前交互。置信度高。

### A08：部分界面直接显示技术异常

**证据。** 例如 [Qbar 初始化](../lib/features/qbar/qbar_panel.ahk)、[词典初始化](../lib/features/dictionary.ahk)、[翻译初始化](../lib/features/translate/llmTranslate.ahk)、[对话初始化](../lib/features/aiChat.ahk)、[笔记初始化](../lib/features/qbar/qbar_notes.ahk) 直接拼接底层异常；笔记图片处理还把 `handleError.Message` 发给页面（352 行）。[设置页](../lib/features/settings.ahk) 已采用通用可操作提示和独立日志，可直接参照。

**影响与建议。** 用户难以据底层英文异常或状态码采取行动，且不符合项目界面约束。统一为“什么操作失败、可以怎么做”，在日志保留阶段和技术细节；共享层可提供小型错误映射，不必重写所有页面。此处是界面与诊断分工问题，本次没有证据证明密钥泄漏或可利用的安全漏洞。

**验收条件。** 所列分支不再把原始异常作为用户文案；日志仍能定位到操作和阶段。置信度高。

## 4. 原结构简化建议（基线快照）

### S01：用一份受信任的动作目录派生元数据

**证据。** 同一组动作信息分散在 [执行白名单](../lib/app/core.ahk)、[自定义快捷键内置动作](../lib/input/customHotkeys.ahk)、[参数校验](../lib/app/settings_store.ahk)、[页面名称与分类](../pages/settings-page.js)。这些集合有不同适用范围，不能简单合并成“所有动作都能用于所有快捷键”。

**建议。** 在宿主源码定义一份动作目录，保存稳定 ID、处理函数引用、名称/分组、参数规则和是否允许无参数快捷键等元数据；白名单、页面快照和候选集合从中派生。执行继续受宿主白名单控制，不把函数代码存入数据库，不按页面传入的函数名动态执行。

**收益与边界。** 新增动作减少多处同步修改，校验与展示更容易一致；这不是已经证实存在某个参数校验缺陷。先迁移少量动作核对等价性，再扩展；保持 `keyFunc_*`、用户 AHK 和现有映射入口的语义。

### S05：限制流响应的诊断缓存，先测量再重写字节管线

**证据。** [SafeArray 转换](../lib/shared/llm.ahk) 生成 AHK 数值数组，[解码](../lib/shared/llm.ahk) 再写入 Buffer；流处理还在 [rawBody](../lib/shared/llm.ahk) 保留每个事件的原始数据，并另行累积已解析正文。非 SSE 响应也有单独的完整字节收集路径。可以确认存在多种数据表示，不能仅凭这一点推断复杂度或实际内存峰值。

**建议。** 先核对诊断、错误解析与非流响应分别需要哪些缓存，优先为成功 SSE 的诊断缓存设置上限，按路径分开保留必要数据；不要裁掉用户回答或非 SSE 回退所需正文。只有代表性长响应的测量证明有实际收益，再调整字节缓冲结构。

**验收条件。** 正常、取消、异常与非 SSE 返回保持现有正确语义；错误诊断仍可用；有固定样本的前后资源数据才宣称性能提升。收益置信度目前不足，此项不应阻塞 A01–A07。

6. **不以体积判定架构。** `core.ahk`、`llm.ahk`、`settings-page.js` 等较大，但“拆文件”本身不改善错误边界。先处理职责重复、失败语义和信任边界；不新增 ORM、事件溯源、通用插件平台或大规模兼容层。
